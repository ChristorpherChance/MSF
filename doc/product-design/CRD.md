## 1. 背景与来源说明

本文档收集软件工厂（MSF）产品**最上游的原始诉求**：用户在 2026-09 期间通过原始提示词、设计想法速览、工作记录反馈与会话决策表达的真实意图，并将其中属于产品范畴的意图结构化为可承接的客户需求条目（CR）。

**追溯链位置**：R（原始诉求，尽量保留原话要点）→ CR（结构化客户需求，本文档 §3）→ REQ（`PRD.md` 产品需求）→ DSG（`HLD.md`/LLD 七册设计条目）。PRD 中 REQ-207（RTM 追踪链）与 REQ-208（需求健康度门禁 L0a=R→CR 覆盖率、L0b=CR→REQ 覆盖率）已预设本层存在；本文档即 MSF 平台产品自身的 R/CR 层，同时是 REQ-208 健康度口径在本产品文档体系中的数据基础。

| R-01 | 把软件项目从客户资料到验收交付组织为一条流水线平台，按阶段推进（资料→需求→设计→开发→测试验收），各阶段在原型中逐版本演进沉淀 | F1 头部「承接 v1.8」；F3（V1.9→V1.11 资料阶段延续）；F5 §6 验收（各阶段回归）；原型 V1.0~V1.11 演进事实 |
| R-02 | 「开发阶段执行完后应接质量检查，主要是开发阶段的自我测试，包括单元测试、前后端联调等」；单测和代码检查在开发过程中持续进行，开发完成后做整体联调、关键业务冒烟和汇总，AI 自动生成报告 | F1 §1 |
| R-03 | 「正式测试前先自我审核，形成自测报告，合格后再转测试」；必测用例通过、质量目标达标、没有阻断缺陷后，**最后由人确认转测试** | F1 §1 |
| R-04 | 「除了功能测试通过，实际 UI 与前期 UI 原型设计也要有很高匹配度，才说明达成目标」 | F1 §2 |
| R-05 | UI 符合度单独作为提测门槛：覆盖页面、布局与视觉、交互、关键状态及响应式；每页一般视觉检查项符合率建议至少 95%，关键项和必测覆盖 100%，严重偏差为 0；截图用于对照和定位，**不以像素相似度冒充业务符合度** | F1 §2（已确认表述） |
| R-06 | 「设计阶段的原型 UI 目前不足，必须把客户需求覆盖到位，并与概要设计和详细设计对应」——先把原型本身做完整 | F1 §3 |
| R-07 | 设计三原则：**需求完整覆盖，设计双向可追溯，内容相互一致**；三类设计共同覆盖全部需求；对应关系检查到具体角色、字段、规则、页面和状态，不只挂文档链接 | F1 §3（已确认表述）；F5 §1 |
| R-08 | 原型流程为「识别页面与流程 → 生成完整原型 → 检查需求覆盖与设计一致性 → 处理问题 → 确认定稿」；定稿形成版本组合与验收依据，后续任务识别和自测使用同一基线 | F1 §3 |
| R-09 | 「保持简单并允许人工参与」：使用者快速看见需本人处理的问题；AI 承担规划、核对、执行和汇总；保留人工操作与暂停接管；页面风格与之前阶段一致，**不增加需要手工维护的复杂表格** | F1 §4 |
| R-10 | 文档的**保存、提交、定稿是三个独立动作**；检查通过不代表用户认可业务体验，定稿仍需人工操作；不得自动替用户确认开发输入 | F2「原型先形成明确的开发依据」 |
| R-11 | 开发自测回答「是否具备提测条件」，最后测试回答「本批候选交付物是否满足已确认需求」；**开发证据可复用为参考，但不能直接变成独立测试的通过记录** | F2「开发自测与独立测试各司其职」 |
| R-12 | **一批交付物，一套不可变证据**：人工确认转测试产生交接回执；测试侧明确接收批次，冻结构建、需求、设计基线、环境和开发自测身份；新构建产生新批次，旧结果不可覆盖或自动沿用 | F2「一批交付物，一套不可变证据」 |
| R-13 | 测试必须落到业务场景（正常、边界、异常）；用例同时区分自动执行与人工验证；**未知覆盖项显示缺口，不由当前实现反推「需求都已覆盖」** | F2「测试必须落到业务场景」 |
| R-14 | **缺陷必须经过修复和回归才能关闭**（失败执行→缺陷确认→修复→新构建提测→回归→测试确认关闭或重开）；修改验收要求走上游变更，不把缺陷改成通过 | F2「缺陷必须经过修复和回归才能关闭」 |
| R-15 | **报告定稿不等于放行**：允许将「不通过」报告定稿留证；放行与有条件放行是独立人工决定，绑定报告与候选批次；有条件放行必须记录逐项风险接受，不清除缺陷、不改失败结果、不授权生产部署 | F2「报告定稿不等于放行」 |
| R-16 | 测试验收保持四个页签（提测与计划/用例与执行/缺陷与回归/报告与交付）；页头始终显示当前批次、当前结论、下一步及阻断原因 | F2「保持四个页签和当前技术边界」 |
