# 原型草稿与历史版本重设计及实施计划

> 执行者须使用 subagent-driven-development 或 executing-plans；同一路线最多两次集中修正。本文只提出新设计，未授权生产实施。2026-09-08。

**目标：** 保留“保存草稿不改版本号、显式提交新版本”的体验，同时确保每个历史检查、共同基线和自测报告始终引用原始版本字节。

**架构：** `S.proto.versions` 只保存不可变版本；新增单个 `S.proto.draft` 承担当前草稿正文及 manifest。当前编辑读取有效工作内容，历史比较只能按版本和指纹读取不可变记录；沿用已验证的纯命令、原子发布和效果恢复。

**技术：** 原生 JS 单 HTML、页面内存；现有 Node、Playwright、Chrome 缓存。

**依据：** `设计基线与自测契约.md`、`原型写事务重设计.md`、`evidence/prototype-transaction-final-review.md`。本文获批准后只替代旧根契约 §2“HTML 只在当前 versions 中、不另建草稿”的权威规则，以及与其冲突的编辑/版本规则；原始冻结文档不改写，引用本文作为追加修订。

## 1. 已确认的问题与停止边界

冻结候选 HTML `32067a815cd0930a25a8a63316e32d5e19cd29c0bc67d9a1fa9306207327e875`、runtime `3b35d12f40caef9b4510568858270e5b5ffb34b8f33e32aacadc38723920f6b9`。

真实路径为：生成、检查、定稿 v1/H0 → 解锁 → 保存 H1 → 提交 v2。当前实现使 v1 与 v2 都变为 H1，H0 消失，而旧基线仍引用 v1/H0。`prototype-version-history-red.json` 覆盖 1 次和 35 次保存，两项均失败。超过 30 次保存又会淘汰最初 undo 项，不能用提交时从撤销栈“找回原文”修补。

这是旧根契约同时要求“当前版本承担草稿”与“历史版本内容不可变”的权威冲突。第二次修正后仍存在结构性缺口，已停止当前路线。已有 65 组通过、客户 GO 和健康构建不能覆盖此失败。

本问题阻断完整 V1.9 交付，直接影响用户要求的 UI 高匹配度及可追溯依据。旧 V1.8、客户模板及 kernel 不受影响。非目标为后端、持久化、任意 HTML 语义理解、多草稿/暂存、真实 Git/CI 和 DevStore 公共契约。

## 2. 单一权威与读接口

```js
S.proto = {
  // 其他现有字段保持原义
  versions: [{ v, at, by, note, html, manifest }], // 追加后整条深只读
  cur: 1,                                     // 选中的已提交版本
  draft: null,                                // 或下述结构
  undo: [], redo: [], modified: false, pend: []
};
// draft 非空时：
({ baseVersion: 1, baseContentFingerprint, html, manifest });
// 新 undo/redo 项保存内容对，不复制作者、时间、版本号：
({ html, manifest });
```

- `versions` 的 v/at/by/note/html/manifest 发布后均不可改写或删除。版本号不能复用，数组只允许追加；生成、导入、提交都是显式追加者。
- `draft` 只属于 `cur`，不含另一个 modified/pending/undo 真源。baseVersion 和 baseContentFingerprint 必须匹配对应已提交记录；失配拒绝操作，不能重绑到当前版本。
- `modified` 由命令同时设置为工作内容对与基准内容对是否不同；不得靠 undo 长度判断。草稿恢复为基准内容时归一化为 null/modified=false，redo 仍可保留。
- `undo/redo` 保留现有 30 项上限，但历史版本保护不依赖它们。记录同时保存 html/manifest；不从当前 manifest 回填历史撤销项。
- 纯接口 `readPrototypeWorking(proto)` 返回当前已提交元数据与有效 html/manifest 的深只读视图，v 仍为 cur；无当前版本返回 null。`curProtoVer()` 只做此只读适配，禁止返回可写的版本/草稿引用。
- `readPrototypeCommitted(proto, versionId, expected)` 只读取 versions。expected 包含 htmlFingerprint、manifestFingerprint、contentFingerprint；缺失、重复版本号或任一不匹配返回 `{ok:false, reason:'HISTORICAL_PROTOTYPE_MISMATCH'}`，不得回退到当前草稿、其他版本或相同标题记录。
- UI、源码、检查、AI 补丁、当前内容指纹读取 `readPrototypeWorking`；历史基线、自测原型比较读取 `readPrototypeCommitted`。完整盘点所有 `curProtoVer()` 与 `versions.find()`，按用途明确归属。

## 3. 转换、发布与失败

| 操作 | 工作内容与历史 | 检查及门禁 |
| --- | --- | --- |
| 保存源码 / 接受补丁 | 首次变更创建 draft，保存工作内容对到 undo；后续只改 draft，清 redo | 当前检查指针清空、状态 generated；已有历史报告不变 |
| undo / redo | 在工作内容对之间转移并重算 modified；不写任何 versions 项 | 同上；空栈无操作不失效 |
| 提议 / 拒绝补丁 | 仅改变现有单 pending 与会话归属；不更改正文 | 沿用启动身份、单 pending、当前消息验证与检查失效 |
| 提交新版本 | modified=true、pending=0；以 draft 内容对追加 v(max+1)，新作者/时间/note；清 draft、undo、redo、modified，cur 指向新版本 | 原 vN 全字段字节不变，新版本须重新检查后才能定稿 |
| 切换版本 | modified=false 且 pending=0 才可切换；draft 必须为空，清工作栈 | 不携带另一版本草稿，当前检查失效 |
| 生成 / 导入 | 无未提交草稿且 pending=0；显式追加完整新版本，清工作状态 | 不静默丢弃草稿；生成/导入期间旧回调继续精确重验当前工作输入 |
| 解锁 | 只改 readiness；不复制、改写或丢失版本 | 立即阻断旧开发依据，沿用幂等观察 effect |
| 定稿 | draft=null、modified=false、pending=0，当前已提交版本上的检查通过 | 基线引用已提交版本及完整指纹，不批准草稿 |
| 参考样本 | 仅 refs 与对应说明 | 不更改正文、版本、draft 或当前检查 |

保存与接受补丁这类向前写入采用以下纯快照转换；undo/redo 使用后面的独立对称转换，不执行向前写入的压栈/清栈步骤：

```js
function normalizePrototypeDraft(proto, content) {
  const base = readCommittedByNumber(proto, proto.cur);
  const changed = !equalContentPair(base, content);
  proto.draft = changed ? {
    baseVersion: base.v,
    baseContentFingerprint: contentFingerprintOf(base),
    html: content.html,
    manifest: clone(content.manifest)
  } : null;
  proto.modified = changed;
}
const before = readPrototypeWorking(next.proto);
if (equalContentPair(before, requestedContent)) {
  return { ok: false, changed: false, reason: 'NO_CHANGE' };
}
next.proto.undo.push({ html: before.html, manifest: clone(before.manifest) });
next.proto.undo = next.proto.undo.slice(-30);
next.proto.redo = [];
normalizePrototypeDraft(next.proto, requestedContent);
```

其中 `readCommittedByNumber` 只返回唯一已提交版本；`equalContentPair` 精确比较 html 与规范化 manifest；`contentFingerprintOf` 使用现有 versionId/htmlFingerprint/manifestFingerprint 公式。重复保存必须在修改 draft、undo/redo、readiness、ID、audit、receipt、DOM 或 timer 之前返回 NO_CHANGE；无论当前为基准 H0 还是已有草稿 H1 都如此。源码保存保留其工作 manifest，不能用新 DOM 重新生成期望以掩盖遗漏；生成与导入才按已有规则产生声明 manifest。

undo/redo 在既有内容对形状已校验、当前版本/草稿不变式成立之后运行如下对称转换；空栈或目标与当前工作内容相同，在 pop/push 和任何其他写入前返回 NO_CHANGE：

```js
const sourceKey = direction === 'undo' ? 'undo' : 'redo';
const targetKey = direction === 'undo' ? 'redo' : 'undo';
const target = next.proto[sourceKey].at(-1);
const before = readPrototypeWorking(next.proto);
if (!target || equalContentPair(before, target)) {
  return { ok: false, changed: false, reason: 'NO_CHANGE' };
}
next.proto[sourceKey].pop();
next.proto[targetKey].push({ html: before.html, manifest: clone(before.manifest) });
next.proto[targetKey] = next.proto[targetKey].slice(-30);
normalizePrototypeDraft(next.proto, { html: target.html, manifest: clone(target.manifest) });
```

`direction` 仅来自已校验的 undo/redo 命令枚举。来源栈只移除目标一项，目标栈追加操作前工作内容；不得清空另一栈。H0→H1→H2→undo(H1)→undo(H0)→redo(H1)→redo(H2) 的 HTML 与 manifest 都须精确恢复；返回 H0 后 modified=false/draft=null，redo 仍保留可重做项。

提交只读有效工作内容并追加，禁止先修改 base 再恢复。`assertPrototypeVersionHistory(beforeProto, nextProto, allowedAppend)` 在发布前验证旧版本数量/次序/唯一编号/所有字段完全等价。统一追加规则为：生成 operation、import-draft 命令、commit-version 命令成功时各恰好追加一条，其余所有操作零追加；失败/no-op 均零追加。`allowedAppend` 由已验证的操作类型内部确定，调用者不能自行指定允许数量。generate 仍属于原有独立设计 operation，不扩充封闭的 12 个内容命令枚举。

三类追加者都令 cur 指向新追加版本，draft=null、undo/redo=[]、modified=false、pending=[]、finalized=false、finalVer=0、currentCheckReportId=''、status='generated'；旧版本各字段保持精确相同。生成和导入已经在写前拒绝 dirty/pending，不能用清理掩盖丢弃；提交在 pending=0 时才允许执行。

发布前还须验证完整工作不变式：`draft===null` 当且仅当 `modified===false`；非空 draft 的 baseVersion===cur、基准指纹与唯一已提交版本重算结果一致、内容对确实不同；versions 非空时 cur 精确命中一个唯一版本，空集合时必须 cur=0、draft=null、modified=false、pend/undo/redo为空、finalized=false、finalVer=0；undo/redo 每项均为独立克隆的 html/manifest 对且各不超过30项；finalized 时 draft=null、modified=false、pending=0、finalVer===cur，未定稿时 finalVer=0。任一不合法应在发布前拒绝，不能自动回填或修正来源。新增版本和旧历史在所有可失败检查通过后深冻结，再发布引用。失败不消费可见版本编号、不修改旧内容、不清草稿/栈、不关闭弹窗。

当前纯命令的快照与发布身份包含整个 proto，因此 draft 自然进入完整冲突身份。AI、定时检查与设计 operation 的当前内容指纹必须改用有效工作内容，版本号相同也不能接受旧回调。

生成的内部设计 operation 也是版本追加者：`tx` 克隆 proto 后、运行内部 mutator 前深冻结历史版本集合；生成改用返回新集合的 `appendPrototypeVersion`，不能 push 到已冻结集合。在成功发布前运行同一历史不变检查；验证和审计之前不得 render/注册 timer。失败恢复原始引用；呈现放在提交后且不能把呈现失败解释为版本回滚。不得恢复已封闭的公开任意 callback 别名，也不把原型写回 DevStore。

## 4. 历史比较、迁移与恢复

历史检查/基线元数据不重写。自测生成 `comparisonArtifacts` 前，按基线版本号与其三项内容指纹调用 `readPrototypeCommitted`；失败拒绝生成合格报告。查看已保存报告时核对其存储的 comparison HTML 指纹，不能只显示版本号。

界面保留当前四步和源码折叠区。草稿状态显示“vN · 未提交修改”，保存不增版本；提交后才出现 vN+1。旧报告照常可查看，当前检查状态与历史通过结论分开。

本原型没有跨刷新持久化，切换采用新 HTML 的干净初始化：`draft=null`，空 undo/redo，既有种子版本深冻结。旧页面不热升级、不导入其 S 对象；刷新按既有产品约定恢复固定示例。旧候选已丢失的 H0 不能凭 undo、报告 hash 或新内容重建，绝不宣称自动修复历史。测试/未来数据导入发现旧字段形状或历史指纹失配时明确拒绝，不将可疑当前内容自动登记成可信历史。

本地 Git 停止检查点与固定 SHA HTML 保留作为可恢复备份；新路线在隔离工作树实施。发布前失败保留原状态；发布后失败只重试已验证的效果，不撤回/覆盖已产生的新版本。main 继续保留 V1.8，客户独立 GO 不改为主流程 GO。

## 6. 自审清单

- 权威冲突已显式替代，不把新草稿藏在闭包、DOM 或 undo 中。
- 旧版本、当前草稿、历史比较三者分开，所有写者/读者均有归属。
- 原始 H0 不依赖撤销上限；HTML 与 manifest 成对保存和验证。
- no-op、失败、旧回调、跨项目、待确认与未提交切换均有反例。
- 当前源码编辑体验保留；客户工件、任务及后端范围不扩大。
- 历史已经损坏时拒绝承诺恢复，不用重新编号或重新签证书掩盖。
