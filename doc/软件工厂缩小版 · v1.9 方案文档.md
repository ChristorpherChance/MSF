## 1. 设计完成标准

🔴 **需求完整覆盖，设计双向可追溯，内容相互一致。** PRD、HLD、7 册 LLD 与完整客户原型共同构成本期设计基线。目录覆盖 16 页、9 条流程、58 种状态、106 个控件、8 个字段和 138 个状态／视口组合；追溯规则同时从文档章节走向目录目标、从目录目标回到实际章节。所有本期需求都要有承接依据；其中 5 项无直接页面的非 UI 要求由概要／详细设计承接，明确不适用原型的原因，不虚造页面。

| 工件 | 责任 | 对应粒度 |
| --- | --- | --- |
| 概要设计 | 模块职责、系统边界、组件协作 | 模块、业务链、约束 |
| 详细设计 | 字段、校验、权限、接口、状态、数据与非功能规则 | 具体规则及文档章节 |
| UI 原型 | 用户可见的布局、操作、反馈与流程 | 页面、控件、角色、状态、视口 |

双向关系允许多对多。正向检查需求是否被设计承接，反向检查页面／操作是否有需求或已确认的支撑设计依据。覆盖成立需要具体内容证据，不以任意登记的 REQ/DSG 编号直接判定。

🔴 本轮基于示例 PRD、概要和七册详细设计生成独立目录 `design-catalog.json`，作为完整性期望。主来源规则 `V19-SOURCE-4` 静态保存 45 个已批准示例章节到 209 个目录目标的双向追溯。先从实时上游建立来源清单并核对目录，再比较原型实际包含的页面与交互；不能从已生成页面反推期望，也不能用目录自证没有遗漏上游。无法识别的新条款标为未验证。原型语义检查是固定示例的可复现规则，不声称能自动理解任意上传 HTML 或任意项目。

🔴 本轮补齐一处客户示例设计缺口：数据库的 `review/draft` 不能独立区分待审核／审核通过待发布，以及普通草稿／被退回草稿。V1.9 的 API 示例新增工作流展示与允许动作字段，保存新示例文档版本及澄清注记；旧版目录保持原样。此项属于已授权的静态示例数据修订，沿用既有示例的已确认上游初始化约定，运行时规划器不能自动改写或定稿用户文档。缺少字段或出现新冲突时仍显示需人工处理。

## 2. 原型识别、生成与共同定稿

🔴 **先识别完整页面与流程，再生成并核对原型。** 页面提供规划摘要、可交互预览、问题列表和定稿入口；沿用现有版本、编辑、上传及修改确认机制。

- 目录覆盖公众门户与 CMS 后台，包含正常、加载、空态、异常、权限、提交成功等适用状态，以及约定屏幕尺寸。
- 页面和流程可定位到需求、HLD 模块、LLD 条目与后续开发任务；检查字段、角色、状态和动作规则是否一致。
- 保留未生成或原有首页原型作为尚未完整的起点，显示具体遗漏；通过识别、生成、检查和人工定稿完成设计，不暗中制造已定稿原型。
- 自动修复仅补齐有明确依据的原型差异；未知需求和设计矛盾必须保留需人工处理。不得自动改变上游设计内容或代人定稿。
- 定稿前必须有针对当前原型内容和当前 PRD/HLD/LLD 版本的有效检查，必需页面／流程／状态缺失、关键冲突和未确认变更阻断定稿。
- 共同基线记录各工件自己的版本组合，不要求所有工件版本号相同。原型或任一相关上游内容变化后，旧检查／基线不可继续作为当前通过依据；重新核对和确认后再进入开发。

设计确认输出：原型版本、页面／流程／状态清单、适用需求与非 UI 承接说明、对应关系、检查结果、UI 自测标准、上游版本组合。

## 3. 开发自测与 UI 符合度

🔴 开发页「质量验收」改为「开发自测」。单任务开发中的单测／CI／独立评审／合并不变；全任务合并并完成当前候选构建后，进行项目级自测，再生成报告。

| 检查 | 合格条件 |
| --- | --- |
| 前端／后端单测、接口契约 | 当前证据有效，必测用例通过；行和分支覆盖率达到各任务批准目标 |
| 前后端联调与关键业务冒烟 | 当前构建上的必测业务矩阵全部通过，无未执行／阻塞／跳过冒充通过 |
| UI 设计符合度 | 本期必测页面与状态覆盖 100%；每个页面在适用视口下关键项 100%、一般项 ≥95%，严重偏差 0 |
| 开发审核与集成构建 | 必需审核、静态检查、候选构建有效且通过 |

UI 符合度按页面核查，不能靠其他页面的平均分掩盖单页不达标。任何 skipped 或 not-run 都不通过。检查项具有设计出处、比较对象、预期、结果和差异；比较的是同一批准原型与同一候选构建。原型预览和实现预览清楚区分，不能两侧都渲染同一对象却声称做过比较。模拟证据必须标注模拟，不宣称真实截图视觉算法或真实服务已执行。

候选构建生成独立的模拟 UI 工件与内容指纹，自测观察该工件后与设计基线比较。自测对照弹窗可选择具体必测状态，并在双方 iframe 加载对应状态；主页面默认不增加这部分复杂度。报告逐页面、逐适用视口判断，不以空关键项集合产生 100%。审核依据按 PR 的实际合并路径保存：自动模式使用独立 AI 评审，人工模式使用既有完整核对项或有理由的人工豁免。

已批准检查标准随设计与计划进入授权快照。AI 不自动降低阈值、删掉失败检查或将失败改成不适用。失败汇总进「需你处理」，定位页面或任务，并提供修订／返工／复测入口，保留旧结果。

## 4. 报告、自动执行与转测试

🔴 自测报告由执行证据自动汇总，不要求使用者重复填报。报告包含：范围与版本、需求覆盖、前后端及联调结果、UI 页面与状态结果、代码审核与构建、问题和复测历史、遗留事项、可提测／不可提测结论。

自动主线：准备计划 → 一次批准 → 开发／单测／评审／合并 → 当前集成构建 → 项目级自测与 UI 检查 → 生成报告 → 待人工确认转测试。

- 报告绑定设计基线、批准计划、原型、候选构建和证据身份；历史报告不可改写，相关输入变化后旧报告不能继续放行。
- 自动模式下无需逐项点击；人工模式可显式开始自测、查看明细、复测和导出报告。
- 暂停、停止、接管只影响当前自动运行拥有的操作，单独人工操作保留独立身份；晚到回调不得写入新运行。
- 必测项目失败或 UI 不达标时停止受阻工作，形成失败报告和明确下一步；同一失败不能空转无限重跑。
- 自测全局单次运行，人工与自动竞争时不互相覆盖；新自测运行期间旧合格报告不能放行。失败复测必须有实际返工与新构建依据，不能仅改构建编号、填写理由或清除故障夹具后宣称修复。
- 只有当前有效且合格的报告才启用「确认转测试」，人工确认后随交接携带报告及设计依据。报告合格不替代正式测试和客户验收。

状态、事务、恢复与反例见《设计基线与自测契约》；该契约须在 HTML 实现前完成独立整体审查。

## 5. 页面与操作负担

- 原型 UI：左侧页面／流程，中央规划、预览和当前问题；右侧继续是现有助手。来源与检查明细按需展开。
- 开发自测：首屏突出结论、需处理问题、检查进度和报告。单测、联调、UI、审核、报告共用同一证据数据。
- 任务识别继续复用统一任务池；设计关联应能从任务查到，也能从页面反查任务，缺少承接任务的设计项保留可见。
- 复用当前颜色令牌、边框、字体和蓝色选中态；1280、1440、1920 及助手开合验证，客户原型另验移动视口。

## 6. 冻结与验收

冻结：真实 AI、Git、CI、后端、通用视觉算法、跨刷新持久化、通用任意 HTML 语义理解、新全局权限系统、自动上游定稿、自动转测试、生产发布。保留原生 JS 单 HTML 离线页面内存原型，刷新恢复种子数据，不重做 DevStore。客户与构建共用 pure kernel；构建必须使用独立 renderer，且不得读取设计 generator。

验收包含：独立目录无缺口，规划不假定稿，完整原型可操作；缺页／状态／字段／权限／来源冲突可检出；过期检查不可定稿；设计基线变更阻断旧开发；功能通过/UI失败不可转测；未执行或跳过不算通过；报告历史和导出身份正确；自动健康链停在人工转测；暂停、停止、接管、手动重跑、旧回调、启动与审计失败可恢复；旧人工及其他阶段回归、旧八版原型不可变。
