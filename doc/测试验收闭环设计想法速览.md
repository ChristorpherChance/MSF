# 测试验收闭环设计想法速览

状态：2026-09-12 用户确认方向；详细设计待审阅，未实施。本文为 V1.9 追加设计，不代表 V1.9 已完成验收。

## 原始诉求

> 设计里，原型UI如何定稿？然后仔细考虑下最后的测试阶段应该如何做

用户随后确认“独立测试验收闭环”的方向。本文件区分原始诉求与据此形成的设计决策，不将后续细节冒充用户原话。

## 原型先形成明确的开发依据

正常路径：识别规划 → 生成原型 → 对应性检查 → 人工定稿。

发生编辑时：保存草稿 → 处理全部 pending → 提交新版本 → 重新检查 → 人工定稿。保存、提交、定稿是三个独立动作。检查通过不代表用户认可业务体验，定稿仍需人工操作。

定稿按钮附近明确显示阻断原因和下一步；定稿后引导进入开发、核对输入、准备计划。不得自动替用户确认开发输入。

→ 详见《测试验收闭环方案文档》§1、§8。

## 开发自测与独立测试各司其职

开发自测回答“是否具备提测条件”；最后测试回答“本批候选交付物是否满足已确认需求”。开发证据可复用为参考，但不能直接变成独立测试的通过记录。

→ 详见方案 §2。

## 一批交付物，一套不可变证据

人工确认转测试产生交接回执；测试侧明确接收批次，冻结构建、需求、设计基线、环境和开发自测身份。新构建产生新批次，旧结果不可覆盖或自动沿用。

→ 详见方案 §3、§4。

## 测试必须落到业务场景

以喀麦隆门户的客户需求为起点，覆盖信息发布、办事申请、双语、CMS角色、检索和开放数据的正常、边界、异常场景。用例同时区分自动执行与人工验证；未知覆盖项显示缺口，不由当前实现反推“需求都已覆盖”。

→ 详见方案 §5。

## 缺陷必须经过修复和回归才能关闭

失败执行 → 缺陷确认 → 开发修复 → 新构建人工提测 → 原场景回归及影响范围验证 → 测试确认关闭或重开。修改验收要求走上游变更，不把缺陷改成通过。

→ 详见方案 §6。

## 报告定稿不等于放行

允许将“不通过”报告定稿用于留证。正常放行和有条件放行是独立人工决定，均绑定报告与候选批次；有条件放行必须记录逐项风险接受，不清除缺陷、不改失败结果，不授权生产部署。

→ 详见方案 §7。

## 保持四个页签和当前技术边界

提测与计划 / 用例与执行 / 缺陷与回归 / 报告与交付。页头始终显示当前批次、当前结论、下一步及阻断原因。

本轮仅原生单 HTML 页内模拟。暂不引入真实测试集群、外部缺陷系统、跨刷新持久化、多租户、真实RBAC或自动生产发布。

→ 详见方案 §8～§10。
