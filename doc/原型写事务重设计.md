# 原型写事务重设计

状态：设计提案，未授权实施。2026-09-08。替代已停止的“事务内调用旧 writer”封装路线，生产代码尚未按本方案修改。

## 问题、收益与范围

当前 `tx()` 只能恢复原型与设计状态；旧保存、提交和上传函数在事务中已经修改事件、通知、会话，渲染 DOM 或注册定时器。最后一步审计失败后，数据回滚而界面显示成功。独立证据 `evidence/prototype-transaction-atomicity-red.json` 分别复现了保存、提交、上传三个反例。这是副作用归属缺口，不能继续在旧函数外围增加快照补丁。

目标是让一次操作的业务结果与用户看到的结果一致。改动仅限 V1.9 原型的内容/readiness 写入，不改客户页面、客户状态 kernel、DevStore、开发任务、构建、自测报告或真实服务。当前阻断整体 V1.9 验收，但不影响旧 V1.8，也不撤销独立客户工件的验证。

## 权威状态与发布边界

一次内容命令涉及的业务权威为 `S.proto`、`S.design.prototype`，以及该命令产生的 `S.events`、`S.notices`、原型会话消息和原型专属恢复收据。收据保存在页面生命周期内的 `V19_RUNTIME.prototypeReceipts`；刷新与其余内存原型一样恢复种子，不承诺跨刷新恢复。DOM、toast 和浏览器 timer 不能作为事务 mutator。

采用三个明确阶段：

1. **准备与纯计算**：从当前状态克隆局部 draft，解析命令、验证项目/定稿/版本/待确认项，建立全部内容变更、stale receipt、设计审计及事件/通知/会话追加记录。只在 draft 上操作；纯函数禁止读取 DOM、全局 `S` 或调用旧 writer、render、toast、logEvent、pushChat、setTimeout。
2. **发布**：再次比对启动时的治理/readiness/内容身份、参与的共享记录引用及规范化内容指纹。指纹包含 events/notices 全内容、原型 sessionId 与消息、当前会话映射、相关业务计数器及收据登记表，能识别同一数组上的原地追加。无 `await`、没有外部调用，在同一 JavaScript 同步栈中替换已准备的状态引用和收据表。所有可能抛错的计算、验证和审计均在发布前完成。发布段仅写现有普通数据属性，不包含 setter、代理、回调或可失败逻辑。业务计数器在 draft 内增长，失败不消耗可见 ID。指纹冲突拒绝整个旧 draft，保留并发追加；不得覆盖后重新补日志。
3. **提交后效果**：依据已提交的不可变结果渲染、显示成功提示，并按需要安排一次对应性检查。UI 效果失败不伪装为业务回滚；返回明确 `committed=true, presentationPending=true`，由结果收据中的 effect key 重试呈现，不重新执行命令、不追加重复业务事件。

所有命令的事件、通知、会话记录均进入同一局部 draft，不能先用 `logEvent/pushChat` 追加后再尝试回滚。共享事件/会话在计算与发布之间有变化时拒绝发布或重新准备，不覆盖他人的追加；本版同步无等待，所以正常 UI 路径不会产生这类交错。

建议内部接口：

```js
preparePrototypeCommand(snapshot, command, context)
// => { ok, next, effects, receipt }，纯函数

publishPrototypeCommand(expectedIdentity, prepared)
// => { committed, receiptId }，只替换准备好的引用

flushPrototypeEffects(receiptId)
// => { presentationPending }，幂等；不重放业务写入
```

命令使用封闭的 `{ type, payload }` 枚举，不接受任意 mutator callback。时间、操作者和不作为业务计数器的随机 nonce 由入口一次捕获后传给纯计算；不在 pure helper 中调用 `now/uid/Date.now`。

## 命令与合法状态转换

| 命令 | 前置条件与 draft 修改 | 对当前设计 operation 的影响 |
| --- | --- | --- |
| save-html | 当前版本存在、未定稿、文本确实不同；保存 undo、清 redo、更新 HTML/modified | 若 running，先换 token、标 stale、追加审计，再写内容 |
| undo / redo | 未定稿且对应栈非空；只操作 draft 历史栈和 HTML | 同上 |
| switch-version | 未定稿、目标版本存在且不同，且 modified=false、pending 为空；否则零写拒绝并提示先提交修改或处理待确认项 | 同上 |
| commit-version | 未定稿且 modified；保存新版本及 manifest，更新当前版本和通知 | 同上 |
| accept-pending / reject-pending | 存在待确认项；接受还要求原文本精确匹配；不匹配整条命令失败 | 同上；失败不清空 pending、不消费 ID |
| propose-pending | AI 结果绑定项目、当前版本/内容；仅追加待确认补丁，不直接确认 | 同上，迟到结果拒绝 |
| import-draft | 未定稿，已完成输入读取与校验；新版本/manifest/消息一次准备 | 同上 |
| unlock | 当前已定稿；清定稿 readiness、登记解锁事件及必需的 observe-dev-input 收据 | 同上；实时开发门禁立即拒绝旧依据，观察失败可恢复 |
| add/remove-reference | 引用样本存在性校验；只修改 refs 和对应消息，允许定稿时管理参考 | 不改变工件/治理身份，不作废当前 operation |

无操作（相同文本、相同版本、空 undo/redo、没有 pending）直接返回未变更；不解锁、不标 stale、不新增审计或通知。

版本切换采用单一工作副本约束：不提供“跨版本保留草稿”或隐式放弃选项，不新增 stash/每版本工作副本。切换前先完成既有保存、提交和待确认处理；干净切换只改变当前版本与其空历史栈，不修改任何版本 HTML。拒绝时版本、草稿、历史栈、pending、ID、审计均不变；下拉框呈现恢复到真实当前版本。验证“编辑 vN→切换被拒→提交为新版本→切 vM→切回”的内容与 modified/undo/redo 归属。

生成/检查/定稿继续使用各自已存在的 operation 事务。旧 `genProto/lintProto/finalProto/doFinalProto` 入口只转发到同一个新服务，不保留可修改工件的旧闭包。旧 `snapProto/save/commit/upload/pending` 函数的变更逻辑迁移为纯 helper，禁止在新事务内调用旧有副作用函数。

## 回调、恢复与失败矩阵

合法内容写入在同一 draft 中旋转当前 operation token 并记录 stale。之后旧 callback 严格零内容、零报告、零指针、零 ID、零审计。绕过正常入口的受信任种子变化，仍由下一公开入口观察并淘汰旧操作；不让旧 callback 反向写审计。

每个收据分为不可变的 `receiptId/projectId/commandId/committedIdentity/effect payload` 和可更新的逐效果 ledger；二者在发布边界内一并登记，不能等到 render 成功后再保存。每项效果有 `effectId/kind/status/payload/attempts/lastError`，状态为 `pending → running → done`，异常为 `failed`，重试 `failed → running`，内容身份过期为 `stale`。完成项和过期项不重放，各项独立捕获异常，失败 render 不阻止记录其他效果的结果；总状态由各项派生。

恢复入口为 `designRecoverPrototypeEffects()`：即使 render 损坏仍可调用；下一次原型公开请求也先恢复当前项目待处理项。函数只刷新 effects，不重放内容命令、版本、事件、通知或会话。render 可重复且只呈现当前状态；modal 关闭按目标 modal 身份幂等；成功提示用 effectId 对应的固定 DOM 标识更新同一条，异常后重试不会重复追加提示。收据明确区分 `presentationPending` 和必需业务效果 `businessEffectsPending`，不能把观察开发输入失败只解释为界面显示失败。

上传后的自动检查包含两项效果：`schedule-check` 注册 timer，取得句柄才标 done；`dispatch-check` 由 callback 执行，注册成功不等于检查执行成功。两者绑定 `projectId/committedVersionId/contentFingerprint`。重复恢复只处理未完成项；注册已发生但抛错导致句柄未知时允许再次注册，但 callback 必须先以同一 dispatch effectId 在同步栈中取得唯一 claim。只有一个 callback 可启动真实检查；其他 callback 退出。调用前失败可重试；调用后结果不确定时先按返回 operationId、operation 输入身份与派发 token 核对现有 operation，找到则登记完成，不能再次启动。检查须经过 `designCheckPrototype()`，可增加内部派发 token 的返回确认，不改变其公共 UI 入口和质量判定。若无法可靠确定是否启动，则保留受阻收据等待显式恢复，不自动重发。切换项目不对另一项目操作；回到原项目且内容身份仍相符才重试，内容已变化则 stale、零业务写。

`unlock` 产生的 `observe-dev-input` 是必需业务效果，其 key 包含项目、解锁前 finalization/readiness 与解锁后身份。发布解锁后，所有推进开发或复用旧计划、批准、构建、自测报告的入口，必须在写前通过现有 `devCurrentInputGate` 与 `designPrototypeGate('develop')` 的实时来源检查；观察暂未登记也必须拒绝旧依据，暂停/停止等收敛动作可保留。不把 `S.dev` 并入原型 publish，也不改变 DevStore 公共契约。

观察效果经现有 `devMarkInputDirty/devReconcileInputs` 登记，只有确认对应 observed input、change/impact/audit 已存在才 done。返回 false、事务/audit 失败或项目不匹配时保留待处理；下一个开发公开入口、回到对应项目或显式恢复时重试。重试先核对既有身份记录，避免追加第二份 change/impact/audit。若原型已再编辑/再定稿，应按当前实时输入统一 reconcile 并将旧效果标记已被该观察承接，不能拿旧收据取消新运行；无法确认承接时保留受阻，不伪造历史成功。这只复用已有观察入口，不新增跨阶段后台调度器。

| 注入点/操作 | 期望 |
| --- | --- |
| 校验、纯内容计算、stale 审计、最终审计任一步抛错 | 所有权威状态、事件/通知/会话、DOM、timer 完全不变 |
| 发布前身份或共享记录变化 | 拒绝旧 draft；不覆盖当前内容或别人的事件 |
| prepare 后对 events/messages 同一数组原地追加 | 指纹冲突拒绝，原地追加保留 |
| 保存/提交/上传发生于检查 A 期间 | 新内容 B 与 stale receipt 同时发布，回调 A 零写 |
| 命令为空操作或定稿不允许的写入 | 全部零写，operation 不无故失效 |
| 发布成功后 render 抛错 | 业务结果保留，明确呈现待恢复；重试只 render，不重复事件/版本 |
| 上传成功后 timer 注册失败 | 工件保留，检查效果待恢复，不显示检查已通过 |
| render 已成功、toast 或 timer 失败后恢复 | 只重试失败项；业务版本/事件/ID不重放，同 key 最多启动一次检查 |
| unlock 已提交，开发观察 audit 失败 | 开发推进立即被实时门禁拒绝；恢复后 change/impact/audit 恰好一份 |
| 修改或 pending 未处理即切换版本 | 零业务写拒绝；处理并提交后才能干净切换 |
| 重试提交后效果/旧效果迟到 | 相同 effect key 最多一次检查；身份不符零写 |
| 切换项目后 AI pending 迟到 | 原项目与当前项目均不被错误写入 |

## 验证与执行边界

同一开放问题包还保留一个独立的来源 issue 格式缺口：下一次实施统一 `issueId/code/severity/target/message/sourceRefs/humanRequired`，ID 从稳定的 code、target、规范化 sourceRefs 派生；严重度为 blocking，plan.issues 和 sourceAudit.unverified 保存同一规范结果。补充失败输入（例如 API 解锁）下的 schema 和相同输入 ID 稳定性反例，不改变已通过的 45/209 双向来源范围。

先把保存/提交/上传现有 3 个真实 RED 扩展为全部命令 × 失败注入点的定向矩阵；再验证一次正常保存→提交→检查→定稿、参考与初稿双通道、AI pending 接受/拒绝、检查中编辑、版本切换、解锁观察恢复及逐效果重试。所有定向反例收敛后，再做独立整体实现审查和候选冻结后的完整回归。延续现有页面风格；唯一明确的操作收紧是未提交修改或待确认项阻止版本切换，并给出先处理再切换的提示。

预计主要编码工作为搬迁约十个局部 writer 的纯状态逻辑；复用已有浏览器环境与夹具，不重建客户 kernel、不重新下载依赖。第一可核对检查点应是 pure command 的失败零写测试；若必须扩大到全局状态容器、持久化或 DevStore 公共契约，立即停止并重新评估。当前只请求审查这一明确方案，未继续生产修复。
