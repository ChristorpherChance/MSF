# 116 公网部署与本机开发环境差异分析

> 2026-10-09 复盘。背景：MSF 软件工厂从 Windows 本机开发环境部署到 116 服务器并公网暴露
> （cc-msf.ikvein.com）后，连续暴露 5 个本机从未触发的问题：AI 对话 500、原型预览打不开、
> AI 对话无流式输出、对话改文档不生效、长流偶发断流。本文回答一个问题：
> **为什么同一套代码，本机跑得好好的，上了 116 就接二连三地坏？**

## 一、结论先行

五个问题的根因各不相同，但共性是同一条：

> **本机开发路径上没有任何中间层，每一个部署态才引入的中间层
> （env 双加载器、nginx 前置、frp 隧道、跨网对象存储、登录门）都携带了一个
> 只在部署态才触发的失效模式。**

本机全绿的测试与实机走查覆盖的是「应用自身的正确性」；而这五个故障全部发生在
「应用与环境的接缝」上——接缝在本机不存在，所以本机永远测不出来。

## 二、两个环境的真实拓扑差异

### 本机开发

```
浏览器 ──直连──> vite :5173 ──代理──> node :18920 ──> docker: postgres/minio/redis (127.0.0.1)
                                      └──> CPA 网关（直连公网）
```

- 浏览器到 API：本机回环，零中间设备
- 浏览器到 MinIO：本机回环（预签名 URL 指向 127.0.0.1:9000，浏览器够得到）
- env 加载：单一加载器，LF 行尾
- 鉴权：未设 MSF_AUTH_USER/PASS，零鉴权直放

### 116 公网部署

```
公网浏览器 ──> nginx/1.18.0（frps 服务器，TLS 终结，proxy_buffering 默认 on）
         ──> frps（8.163.127.192）═══ 公网隧道 ═══> frpc（116）
         ──> node :18920 ──> docker 三件套（127.0.0.1，MinIO 公网不可达）
                       ──> CPA 网关（116 出网，路径与本机不同）
```

多出四个中间层 + 两个状态差异：

| # | 差异点 | 本机 | 116 部署 |
| --- | --- | --- | --- |
| D1 | env 加载器 | 单一（LF .env） | 双口径：bash `source` 留 `\r` / systemd EnvironmentFile 剥 `\r` |
| D2 | MinIO 可达性 | 浏览器与 MinIO 同机，预签名直链可用 | MinIO 只绑 127.0.0.1，公网浏览器够不到 |
| D3 | HTTP 中间层 | 零（vite 代理不缓冲 SSE） | nginx（缓冲）+ frps/frpc（隧道） |
| D4 | 鉴权态 | 零鉴权，cookie 路径从不执行 | 登录门开启，401/cookie 路径首次被真实流量执行 |
| D5 | AI 上游路径 | 本机出网直连 | 服务器出网，长流存活暴露面不同 |
| D6 | 文件来源 | 本地生成（LF） | Windows 编辑 scp 上传（CRLF 风险） |

## 三、五个故障逐个解剖

### 故障 1：AI 对话 500（CRLF 密钥灾难）

| | |
| --- | --- |
| **现象** | 所有需要解密 API key 的 AI 调用 500：AES-GCM「Unsupported state or unable to authenticate data」 |
| **根因** | `msf.env` 从 Windows 带过去是 CRLF 行尾。bash `source` 时值含尾部 `\r`（密钥 62 字符），systemd EnvironmentFile 剥 `\r`（61 字符）。重加密脚本用带 `\r` 的 key 加密，应用用干净 key 解密——密钥差一个字节，GCM 认证必然失败 |
| **为何本机不犯** | 本机 .env 是 LF，且只有一个加载器——「同一份密钥两种读法」这个前提在本机不存在 |
| **修法** | `sed -i 's/\r$//'` + 以 `\r`-key 为旧根重跑换根重加密（10 处换新，正确跳过 1 处本就正常的） |
| **差异点** | D1 + D6 叠加：CRLF 文件（D6）遇到双口径加载器（D1）才爆炸 |

### 故障 2：原型预览打不开（MinIO 预签名不可达）

| | |
| --- | --- |
| **现象** | 原型预览 iframe 加载失败；下载类链接同样打不开 |
| **根因** | `presignedGet` 签出的直链指向 `MSF_MINIO_ENDPOINT=127.0.0.1:9000`。MinIO 容器只绑回环，公网浏览器拿这个 URL 去连自己电脑的 9000 端口 |
| **为何本机不犯** | 本机浏览器和 MinIO 就在同一台机器上，127.0.0.1:9000 恰好可达——**这是一个「恰好能跑」的隐性假设**，代码里没有任何东西错，是环境拓扑变了 |
| **修法** | 新增 `MSF_FILES_PROXY=1` 分支：预签名改发本进程代理相对 URL `/api/v1/files?key=…`，由应用流式转发（走登录 cookie 鉴权）。7 个签发点一处改全受益；本地不设该 env 行为不变 |
| **差异点** | D2 |

### 故障 3：AI 对话没有流式输出（nginx 整包缓冲）

| | |
| --- | --- |
| **现象** | 发消息后长时间无字，最后整段回复瞬间出现 |
| **根因** | 公网链路多一层 nginx（frps 服务器上终结 TLS），默认 `proxy_buffering=on` 把 SSE 响应**攒到结束才吐**。对照实验钉死：同一接口 LAN 直连 116 是 17 个 chunk 分 3 秒增量到达，走公网域名合成一个整包 |
| **为何本机不犯** | 本机链路上没有任何反代；vite 代理不缓冲 SSE |
| **修法** | 全部 6 个 SSE 端点加 `X-Accel-Buffering: no` 响应头（nginx 标准直通约定）。修后公网实测 17 chunk/4.7s 增量到达 |
| **差异点** | D3 |
| **附带教训** | 之前的「流式验证」都用 `await res.text()` 收全量——验证不了「是否增量到达」。**流式功能的验收必须测增量时序**（首 chunk 与末 chunk 的时间差），不能只测收全 |

### 故障 4：对话改文档不生效（接力轮上限耗尽）

| | |
| --- | --- |
| **现象** | 模块设计册对话「请重新生成当前文档」，AI 回了一段承诺文字，页面没有任何变化 |
| **根因** | AI 按阶段指南先诊断：读 mod/prd/hld + 分页补读共 7 次 doc.read；接力循环封顶 3 轮被读操作耗尽，propose_edits 提案没来得及发，末轮未执行的围栏原文还残留在消息尾 |
| **为何本机不犯** | **会犯——这不是环境差异**，是同版本共性缺陷，只是读密集型长任务在本机测试里没被点到。列入本文是因为它在部署实机上暴露、且与故障 3 叠加放大了「AI 没反应」的体感 |
| **修法** | 上限 3→8（防失控靠「回复无工具围栏即停」而非轮数）+ 末轮警告 prompt + 封顶善后（剥未执行围栏 + 消息内「回复继续」入口） |
| **实机回归** | 重发同请求 → 4 次读取 → propose_edits 整篇重写提案 pending 落库 |

### 故障 5：长流偶发断流（上游瞬断）

| | |
| --- | --- |
| **现象** | 原型页级生成流到 4411 个 delta 后被切断，报 MODEL_UNAVAILABLE |
| **根因** | 应用到 CPA 网关的长连接偶发瞬断（closed before response.completed）。直连压测两种 API 各 100 秒+ 长流均完整——是随机瞬断，非系统性超时 |
| **为何本机不显眼** | 概率性事件；本机出网路径不同、测试轮次少，没踩到 |
| **修法** | 三处生成驱动统一包有界自动重试（断流分类器排除 429/401/配额；文档域 1 次、原型页级 2 次；重试发 stream.notice 帧前端 toast，不静默） |

## 四、模式归纳：五类「部署态才发作」的失效模式

| 模式 | 本案实例 | 通用防线 |
| --- | --- | --- |
| **同份配置的两种读法** | 故障 1：bash source vs systemd 对 `\r` 口径不一 | env 文件强制 LF（入库钩子/部署脚本检查）；密钥类操作打印长度指纹供对账 |
| **「恰好能跑」的地址假设** | 故障 2：预签名 URL 假设浏览器与 MinIO 同机 | 凡是签给客户端的 URL，反问一句「客户端在哪台机器上」；部署态加代理开关 |
| **中间层默认行为** | 故障 3：nginx proxy_buffering 默认 on | SSE/长轮询端点一律带 `X-Accel-Buffering: no`；链路图画全（包括别人的服务器上的那一层） |
| **概率性故障在长尾暴露** | 故障 5：瞬断重试 | 长调用一律有界自动重试 + 可见提示；「测一次通过」不代表「没有概率故障」 |
| **资源上限被真实负载打满** | 故障 4：接力 3 轮上限 vs 7 次读取的真实流程 | 上限值要用真实最重负载校一遍；触顶必须有善后（不能让半截状态裸奔） |

## 五、方法论沉淀：这次哪些排查手段最见效

1. **对照实验隔离链路层**：同一请求分别走「公网域名」与「LAN 直连」，行为不同即证明问题在中间层而非应用（故障 3 一定位到 nginx 就靠这招）。
2. **增量计时探针**：流式功能用「首 chunk/末 chunk 时间差 + chunk 数」判定真流式，补上了此前全量收取式验证的盲区。
3. **数据库即现场**：ai_messages / ai_tool_calls / dsg_pendings 三张表完整还原了「AI 承诺了但没执行」的全过程——工具调用留痕纪律（设计时的 W2 系列要求）在排障时兑现了价值。
4. **绕过应用直测上游**：从 116 直连 CPA 网关压测长流，一次排除「网关系统性超时」的嫌疑，把故障 5 定性为概率瞬断，避免了过度修复。

## 六、仍存在的已知差异（备忘）

| 项 | 现状 | 风险 |
| --- | --- | --- |
| 长思考静默期 | 模型长思考时 SSE 可数分钟无字节；nginx/frp/浏览器实测耐受，Node fetch 客户端默认 bodyTimeout 300s 会自杀（仅探针脚本受影响） | 低；如需再硬可加 `: ping` 心跳（前端解析器本就容忍非 JSON 行） |
| 服务器算力 | i5-6400 / 15GiB，与本机有差距 | 生成时长更长属预期；沙箱执行类任务关注资源上限 |
| 单副本 | 单进程无高可用 | 与产品定位（单机/小团队）一致，不视为缺陷 |
| 登录门强度 | 简易用户名密码 + 限流 | 满足当前内网级暴露口径；公网长期化再评估加 MFA/审计面 |
