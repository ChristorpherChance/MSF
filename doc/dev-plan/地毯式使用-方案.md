# 地毯式使用方案：以产品使用团队视角全流程使用 MSF 软件工厂

**日期**：2026-09-27
**角色设定**：产品使用团队的一名工程师，拿到一个真实需求输入（智能代码审查系统设计说明书），要用本平台从零交付一个软件项目。
**与开发走查的区别**：不走后门、不直连数据库、不调用测试钩子；一切操作经 Web UI（个别 UI 未覆盖的查询用只读 API 佐证）。发现问题不现场修，记入《地毯式使用-问题与疑问.md》。
**使用对象**：本地部署实例（apps/web :5173 + apps/server :8080 + postgres/minio/redis，AI 走 pi 真实网关）。

## 一、使用目标

1. 验证「资料 → 需求 → 设计 → 开发 → 测试验收」五阶段主线能否由真实用户独立走通，不依赖开发者知识。
2. 地毯式覆盖每个页面的每个可操作控件（按钮/页签/过滤/弹窗/空态/错误态），而非只走 happy path。
3. 记录三类发现：**系统问题**（报错/卡死/数据错误）、**体验疑问**（不知道该点什么/文案看不懂/流程断点）、**改进建议**（能做但绕路）。

## 二、前置检查（S0）

| 步骤 | 操作 | 预期 |
|------|------|------|
| 0.1 | 打开首页 /projects | 项目列表、新建入口、归档区可见；导航栏五阶段+Task+委派+设置可达 |
| 0.2 | 检查既有项目卡片 | 阶段标签、成本、操作按钮（编辑/进入/归档）语义自明 |
| 0.3 | 新建项目「地毯使用-智能代码审查系统」 | 创建后落到资料阶段；空态引导语看得懂 |
| 0.4 | 项目编辑/描述、切换项目 | 当前项目标识清晰，切换不串数据 |

**输入材料准备**：用 `test/赛道3-基于n8n的智能代码审查与质量管理系统--设计说明书.pdf` 作主输入（真实文档），另造 md/txt/docx/zip 各一份试探格式覆盖与 ZIP 安全校验。

## 三、分阶段场景

### S1 资料域（目标：把原始输入变成「已定稿参考」）

| # | 场景 | 覆盖点 |
|---|------|--------|
| 1.1 | 上传主 PDF（分片上传） | 进度、完成后解析状态、去重提示 |
| 1.2 | 上传 md/txt/docx 各一 | 扩展名接纳、解析成功率 |
| 1.3 | 上传 zip（含嵌套目录） | ZIP 校验链行为、拒绝文案是否人话 |
| 1.4 | 目录管理 | 新建/重命名/删除空目录/删除非空目录的守卫 |
| 1.5 | 解析结果查看与编辑 | 双树、三态编辑器、保存草稿 |
| 1.6 | 内容定稿（单件+批量） | 定稿门禁、批量弹窗五态、失败行级反馈 |
| 1.7 | 文件删除 | 引用守卫、留痕语义 |
| 1.8 | 参考资料候选确认（references） | verifyReferences 供下游 |

### S2 需求域（目标：CRD/PRD 定稿，RTM 健康达标）

| # | 场景 | 覆盖点 |
|---|------|--------|
| 2.1 | 生成 CRD（勾选参考资料） | 参考选择、SSE 流式过程、指纹透出 |
| 2.2 | CRD 编辑与补丁处置 | 逐节编辑、乐观锁冲突提示、补丁接受/拒绝+理由 |
| 2.3 | 定稿 CRD | 定稿后只读、版本固定 |
| 2.4 | 生成 PRD（基于 CRD） | 上游引用、生成中取消/暂停语义 |
| 2.5 | PRD 定稿 + RTM 门禁 | L0 四指标实算、缺口提示是否可行动 |
| 2.6 | 导出 docx/pdf/md | 文件名、内容完整性 |
| 2.7 | RTM 页 | 四层级表、deferred 行、反向追溯 |

### S3 设计域（目标：八册定稿 + 原型定稿 + 基线确认）

| # | 场景 | 覆盖点 |
|---|------|--------|
| 3.1 | 生成 HLD（📚参考资料 popover：默认上游+追加勾选） | 参考装配口径、生成参数 |
| 3.2 | 其余七册依次生成定稿 | 册间一致性、定稿门禁 |
| 3.3 | 设计评审 DR | 问题提出/解决/重开 |
| 3.4 | 原型：识别→生成→检查→定稿 | 目录条目、UI 检查矩阵、锚点 |
| 3.5 | 原型页追溯区 | 需求/锚点/任务/流程四组反查 |
| 3.6 | 确认共同基线 | 基线工件表、指纹、失效演示（上游再定稿→基线过期提示） |
| 3.7 | 导出设计册 docx/pdf | 文件名带册名与版本 |

### S4 开发域（目标：准备计划→批准→自动执行→转测试）

| # | 场景 | 覆盖点 |
|---|------|--------|
| 4.1 | ✦ 准备计划 | 建议生成（create-task/patch-task）、六指标、proposals 卡四态 |
| 4.2 | 建议处置 | 采用/不采用/查看修订 modal、旧修订只读、指纹变化 |
| 4.3 | 批准并自动执行 | 未处置拦截、新鲜度失效提示、ConfirmModal 双联 |
| 4.4 | 看板观察自动执行 | 阶段标签、任务卡流转、失败 blocker 呈现 |
| 4.5 | 人工任务处理 | HUMAN_TASK_REQUIRED 阻断、人工接管 |
| 4.6 | 手动操作条 | 识别/核对覆盖/完善任务/编排计划/提交版本（人工路径可达性） |
| 4.7 | 任务详情编辑 | 全字段表单、规格问题实时提示、覆盖确认 |
| 4.8 | 暂停/停止/接管运行 | token 旋转语义的用户可感知面 |
| 4.9 | 自测四门与报告 | 单测/PR/构建/项目自测、报告导出 |
| 4.10 | 变更管理 | 影响处置、基线重确认、计划与审计时间线 |
| 4.11 | 确认转测试 | 门禁、人工确认、交接单 |

### S5 测试验收域（目标：批次→执行→缺陷→报告→放行决定）

| # | 场景 | 覆盖点 |
|---|------|--------|
| 5.1 | 创建测试批次 | 用例计划版本化 |
| 5.2 | 执行用例 + 人工验证记录 | 两级执行、通过/失败证据 |
| 5.3 | 登记缺陷 → 修复回流开发 → 回归关闭 | 缺陷五态、阻塞语义 |
| 5.4 | 汇总报告 | 结论横幅、定稿不通过的路径 |
| 5.5 | 人工交付决定（放行/不放行） | 不可变留痕、导出报告与决定 |

### S6 横切面（任何阶段顺带观察）

| # | 场景 |
|---|------|
| 6.1 | AI 助手 dock（F1）：问答、上下文引用 |
| 6.2 | 委派页：发起/跟踪/重跑 |
| 6.3 | 任务中心：异步作业列表与回执 |
| 6.4 | 通知中心：事件到达与跳转 |
| 6.5 | 设置：AI 模型路由、提示词版本、CI webhook 密钥（只写不读） |
| 6.6 | 成本台账（💰）：用量记录是否合理 |
| 6.7 | 错误呈现：断网/后端重启后的前端表现、错误码是否人话 |

### S7 压力与边界（选做，视时间）

- 生成中途刷新页面 / 关闭再打开（恢复语义）
- 同一操作连点两次（幂等键行为）
- 两个浏览器标签同时操作同一对象（乐观锁提示）

## 四、记录纪律

1. 每完成一个场景立即在《地毯式使用-问题与疑问.md》登记：编号 U-xxx、严重度（阻断/严重/一般/建议）、现象、复现步骤、预期 vs 实际、截图/证据。
2. 疑问类（不确定是不是问题）单独标记「疑问」，不猜测结论。
3. 本次使用**不修代码**；所有发现只登记。
4. 中文提交一律经 Python/文件写盘（curl -d 经 Git Bash 会 GBK 乱码——已知坑）。
