# 模板重排批量刷新（⇄ 模板重排）· 设计

> 2026-10-11 立项。定位（用户拍板）：**产品化批量功能**——任何项目在模板升级或文档漂移后，
> 可将存量文档按当前生效模板骨架批量重排；覆盖**全部十类文档**（crd/prd + 设计八册）；
> 确认节奏为**逐册流水线**（边产边确认，复用既有补丁确认 UX，零新确认面）。
>
> 与预防体系的关系：生成链模板硬注入（初稿/rewrite）+ rewrite 骨架默认化（B2）是预防；
> 本功能是**核验+修复**——启发式徽标常态化轻核对，批量重排是核验不通过时的修复通道。
> 预防漏网三类场景：存量旧册（模板体系建立前产物）、增量漂移（增量通道有意不注入模板）、
> 模板自身升级后的全量重核。

## 1. 架构与组件

后端三新件 + 全量复用既有设施；**零新表、零新错误码**。

1. **`template-refresh.service.ts`**（platform 模块）：批量任务编排器。内存任务注册表
   `Map<opId, RefreshOp>`（沿用 GenOp 先例；进程重启丢任务=已知限制，已出提案不受影响）。
   RefreshOp：选定 kind 队列、每册状态机
   `queued → running → done / failed(reason) / skipped(reason)`、进度事件滚动窗（≤200，断线重放）。
2. **每册执行处理器走注册表模式**（镜像 external-tools.ts 先例，零模块图边）：
   req/design 两个 generate.service 在 onModuleInit 各注册 `refreshHandler(kind) → {ok, reason?}`，
   内部直接调用**既有 proposeEditsFromChat**（`mode:'rewrite'` + 固定 instruction
   「按默认模板骨架重排整篇：内容按主题归入模板大章，保留有效锚点码与编号，不增删需求语义」）。
   rewrite 骨架默认化已上线，提案语义天然正确；A2 断流重试在 proposeEditsFromChat 内部兜底。
3. **端点四个**（实现口径=平铺子路径，区别于冒号自定义动作）：`POST /api/v1/projects/:pid/template-refresh/start`（命令落审计，
   Idempotency-Key 头，返回 operationId）；`GET .../template-refresh/preflight`
   （弹窗数据：十册清单+启发式徽标+跳过预判，§3）；`GET .../template-refresh/:opId/stream`
   （SSE 进度，`X-Accel-Buffering: no` + 15s `: ping` 心跳，A1 模式套用）；
   `POST .../template-refresh/:opId:stop`（轻量停止，§2——此条为冒号动作，与仓库 `\:stop` 先例同款）。

前端两新件：需求页/设计页工具栏「⇄ 模板重排…」按钮（弹窗覆盖全部十类、按域分组勾选）
+ 进度面板（每册一行：状态徽标+原因+「去确认 »」跳转）。

复用清单：proposeEditsFromChat（守卫链+提案落库+usage 落账）、doc.propose-pending /
design.doc.propose-pending、补丁确认 UX（需求页/设计页既有）、window 事件
msf:req-proposed / msf:dsg-proposed、splitSections、resolveTemplate 三级链、
isRetryableStreamCut / withStreamCutRetry、SSE 心跳与 X-Accel-Buffering 模式。

## 2. 数据流与执行语义

**启动**：前端勾选 kinds → `POST :start`（Idempotency-Key）→ 命令校验
（kinds ⊆ 十类、去重、同项目无活跃批次——冲突用既有 INVALID_STATE 人话「已有批量重排进行中」）
→ 落审计 → 建 RefreshOp 入注册表 → 返 operationId → 前端立刻挂 SSE。
编排循环在服务端后台跑，不挂请求。

**逐册串行循环**（每册）：

1. **守卫预检**（与 proposeEditsFromChat 同口径，预检目的=区分 skipped/failed）：
   无内容 → skipped「未生成」；已定稿 → skipped「已定稿，需先解锁」；
   有 pending 补丁 → skipped「有待确认补丁，先处置」。
2. 发帧 `refresh.kind.started {kind}` → 调 refreshHandler →
   成功：pending 提案落库，发 `refresh.kind.done {kind, patchCount:1}` + 服务端侧标记使前端
   广播 window 事件（msf:req-proposed/msf:dsg-proposed 同款——打开着的需求/设计页补丁区
   自刷新，用户即刻可处置该册，流水线确认成立）；
   失败：发 `refresh.kind.failed {kind, reason 人话}`，**继续下一册**（失败隔离）。
3. 全队列完 → 终帧 `refresh.done {summary: {done, failed, skipped, skippedReasons}}`
   + 操作落终态。

**SSE 协议**：帧型闭集五种（`refresh.kind.started/.done/.failed/.skipped` + `refresh.done`），
前端 else 兜底前显式分支（差异登记条目 37 教训帧纪律）；断线 `lastEventId` 重放
（进程内滚动窗 ≤200，批量任务生命周期短，无 Redis 镜像）。

**停止**：`:stop` 置标志位——当前在飞册跑完、剩余队列标 skipped「人工停止」。
**不**做中断在飞册（嵌套 AI 会话无外部 abort 句柄，登记已知限制）。

**下游联动零新增**：提案被人工接受并提交后，既有上游变更派生机制自动标 stale
（PRD 变→设计八册滞后徽标；设计册变→开发基线 BASELINE_STALE）；批次终帧 summary
附提示「确认完毕后请回设计页重新确认基线」。

**用量**：每册一次 ai.usage.record（purpose='generation'，session NULL=真无会话调用，
A6 口径自洽），dock 统计面板「文档生成等」桶正常计数。

## 3. 启发式判据、异常与边界

**「与模板不对版」启发式**（用户拍板要；只提示不拦截）：start 前的预检读侧（弹窗数据端点
`GET .../template-refresh/preflight`）对每册：取当前有效稿（草稿优先，doc.read 同口径）
→ splitSections 大章标题集 vs resolveTemplate 当前生效骨架（用户套件覆盖也算）——
**缺章 / 多章 / 顺序不符**任一命中即标黄「与模板不对版」；无内容标「未生成 · 将跳过」；
已定稿标「已定稿 · 将跳过」。纯格式比对，命中≠内容差——弹窗副标题注明
「仅格式启发式，最终以你的判断为准」。

**异常矩阵**（全人话，零新码）：

- start 校验失败（kinds 空/越界/同项目活跃批次冲突）→ VALIDATION_FAILED / INVALID_STATE，前端 toast；
- 单册 AI 调用失败（含 A2 重试后仍败）→ 该册 failed，原因=sanitizeAiError 脱敏人话，继续下一册；
- 提案落库竞态（PATCH_BASE_STALE / VERSION_LOCKED / INVALID_STATE）→ 该册 failed
  「文档已被变更，请刷新后重试」；
- 批次进行中进程重启 → 任务丢失（内存注册表口径），前端 SSE 断开提示
  「批次中断，已出提案不受影响，可重新发起」；
- 全册跳过 → 终帧 summary 全 skipped，不视为失败。

**边界**：批次期间某册被人工定稿/处置 → 轮到该册时守卫链实时重查，自然 skip（不锁册）；
多标签页打开同批次进度 → SSE 广播天然支持。

**预防补条**（用户拍板同批落地）：stage-guides REQ_GUIDE / DESIGN_GUIDE 各补一句
模板纪律——「生成与提案修订时遵循当前生效模板骨架（📄 模板钮可查）；发现文档结构与模板
不对版时，提醒用户可用「⇄ 模板重排」批量修复」。

## 4. 前端 UX（效果样机已过目）

静态样机 `.tmp/template-refresh-mock.html`（2026-10-11 用户浏览器过目确认）三态：

1. **入口与选册弹窗**：工具栏「⇄ 模板重排…」→ 十类按域分组勾选、启发式徽标行内、
   底部「已选 N 册 · 预计 30~70 分钟」+「提案经你逐册确认后才生效」明示；
2. **批量进行中**：每册一行（生成中转圈「约需数分钟」/提案已出「去确认 »」/已确认生效/
   跳过+原因/排队中），底部「⏹ 停止剩余」「后台运行（关闭面板不中断）」；
3. **批次收尾**：汇总条（已出/已生效/跳过/失败）+ 失败册「重试该册 »」
   + 「请回设计页重新确认基线」提示。
   「重试该册 »」机制=批次终态后以 `kinds=[该册]` 重新 `POST :start`
   （并发闸在批次终态后放行，天然支持）——**不**设单册重试端点。

样式纪律：全 var() 设计令牌，禁写死颜色；toast kind 只用 default|success|warn。

## 5. 测试口径

- **单元**（本机可跑）：启发式判据（缺章/多章/逆序/一致四形态）；kinds 校验（空/越界/去重）。
- **集成**（101 跑）：注册 fake refreshHandler 走编排器——顺序执行/失败隔离
  （一册 throw 后续照常）/全跳过汇总/SSE 帧序（started→done/failed/skipped→refresh.done）/
  stop 后剩余标 skipped/并发闸第二批 INVALID_STATE；
  mock provider 真链路两册（crd+hld）端到端：start→pending 落库→帧序→summary。
- **契约**：固定 instruction 文案断言——instruction 常量定义在 template-refresh.service.ts
  （编排器单点持有，req/design 处理器共享），断言挂 doc-prompts.test.ts 引常量比对。
- **回归**：既有 295 基线全绿 + 新增；实机（部署 116 后）对 2 册发起批次，
  观察 SSE 进度/心跳保活/提案落库/确认回环。

## 纪律与登记

- 错误码闭集不加码；审计失败零写；人工确认/定稿不破（本功能只产 pending 提案，确认永远人工）。
- console 只 warn/error；含中文 API 一律 node fetch；临时脚本用完即删。
- 差异登记追加条目 42（本功能），13 册回补目标：LLD-2 F11、LLD-5 A04、LLD-6 U02/U03。
- tsc 双端 + pnpm lint + check-codes 零违规；101 全量（排除 sandbox/storage 两环境性套件）。
